# 时间轴运行时实现说明

这份说明记录 `addons/nv_timeline/` 当前运行时行为。业务回调及其异步过程由使用项目管理；插件只负责时间轴游标、阻塞标记、消息顺序和结果校验，不创建或追踪业务处理对象。

## 已实现的 C++ 类型

- `NVTimelineDocument`：读取/保存 `.timeline.json`，执行字段白名单、类型、ID 唯一性、时钟引用、时间范围、标签和颜色校验。
- `NVTimelineClock`：维护 0.1 秒整数时间单位；`manual` 由 `advance_units` 推进，`realtime` 在 Service 的 `_process` 中累计实际秒数和倍率。
- `NVTimelineRuntime`：把启用轨道中的 marks 展平为稳定顺序，维护运行 ID、游标、暂停、完成和阻塞等待状态。
- `NVTimelineEventManager`：维护 FIFO 统一请求队列和 Godot `Callable` 绑定；回调收到统一 Dictionary 上下文。
- `NVTimelineService`：持有全部时钟、平级时间轴和唯一事件管理器，负责实时驱动、标签路由、诊断信号和运行控制。

## 首版调度规则

设计稿中列出的未定调度细节在第一版采用以下确定规则：

1. 同一时间点按 `tracks` 数组顺序，再按 `marks` 数组顺序求值。
2. 一次普通时钟推进会检查区间内全部标记；遇到未满足的阻塞输入或等待结果的输出时，所属时间轴停在该位置，不处理更晚标记。
3. 普通时钟推进遇到阻塞时丢弃本次剩余单位；共享时钟继续推进，其他时间轴不受影响。
4. 同一个标签可以同时记录到一条时间轴的多个阻塞输入和全程输入。
5. 时间轴暂停时全程输入和阻塞输入仍接收标签；暂停期间收到输入只解除等待，恢复请求仍需由程序提交。
6. 标签、时间轴控制、快进、跳转和阻塞输出结果共用 FIFO 队列；回调中新提交的请求排到当前请求之后处理。
7. 快进遇到阻塞时保存目标位置；成功解除阻塞后继续处理到原目标。失败结果停止本次时间轴运行。
8. 跳转只允许向前，直接略过目标位置及之前的标记，不补发输出、不等待阻塞输入。
9. 时间为 0 的输出标记在启动时求值；有限时长到达末端且没有未完成标记时发出 `timeline_completed`。

这些规则属于运行时实现，不会增加 JSON 字段；未来若需要改变，应该通过 API 或版本说明调整，而不是把事件处理逻辑写进编排文件。

## Godot 使用入口

构建根项目后，将 `res://addons/nv_timeline/nv_timeline.gdextension` 保持在项目目录中即可加载原生类。典型调用顺序如下：

```gdscript
var service := NVTimelineService.new()
add_child(service)
service.load_json_file("res://addons/nv_timeline/examples/basic.timeline.json")
service.start_timeline(2)
service.advance_clock(1, 10)
service.publish_label("demo_confirmed")
```

业务代码通过 `service.get_event_manager().register_binding(label, callable, requires_timeline_input)` 登记处理回调。回调上下文包含 `label`、来源时间轴和运行 ID、逻辑时间、已接收时间轴 ID 与输入 ID。若输出标记设置了 `wait_for_result`，上下文还包含 `output_mark_id` 和 `wait_for_result: true`。业务代码可以自行等待 UI、玩家输入或其他异步工作，之后通过 `submit_request` 返回成功或失败；插件不会保存处理器对象、执行时长或内部步骤。

可视化编辑器的输出标记属性面板提供“等待业务结果”开关；该开关只对 `kind: output` 显示，保存时对应写入或删除 `wait_for_result` 字段。阻塞输入不允许配置该字段。

### 统一请求入口

`service.submit_request(request)` 将请求追加到统一 FIFO 队列，并在安全的派发轮次中处理。返回值只表示请求结构有效且已入队，不表示目标操作一定成功。事件回调中应使用此入口，避免在当前标签的接收遍历期间直接改写运行状态。为兼容已有项目，原有 `start_timeline`、`pause_timeline`、`resume_timeline`、`stop_timeline`、`advance_clock` 和 `publish_label` 仍保留。

请求类型共 9 类：

| `type` | 必要字段 | 行为 |
|---|---|---|
| `publish_label` | `label` | 发标签；可选 `target_timeline_id`，为 0 或省略时广播 |
| `start_timeline` | `timeline_id` | 启动一条时间轴 |
| `pause_timeline` | `timeline_id` | 暂停一条时间轴 |
| `resume_timeline` | `timeline_id` | 恢复一条时间轴 |
| `stop_timeline` | `timeline_id` | 停止一条时间轴 |
| `advance_clock` | `clock_id`、`units` | 按 0.1 秒单位推进时钟 |
| `fast_forward` | `timeline_id`、`target_units` | 按序求值并快进到绝对位置，阻塞通过后继续到目标 |
| `jump` | `timeline_id`、`target_units` | 向前跳到绝对位置，跳过期间标记 |
| `resolve_output_result` | `timeline_id`、`run_id`、`mark_id`、`success` | 返回等待输出的成功或失败结果 |

表内的九种 `type` 是 `submit_request` 接受的全部公开请求类型。派发队列内部会把标签消息归一为 `label`，但该内部类型不能通过 `submit_request` 直接提交；业务代码发标签时使用 `publish_label`。

示例：

```gdscript
service.submit_request({
	"type": "resolve_output_result",
	"timeline_id": context["source_timeline_id"],
	"run_id": context["source_run_id"],
	"mark_id": context["output_mark_id"],
	"success": true,
})
```

结果使用所属时间轴 ID、运行 ID 和输出标记 ID 校验。时间轴重新启动后，旧运行回调携带的结果会被忽略。若多个绑定同时处理同一个等待输出，首个有效结果生效；其余迟到结果会被忽略。具体业务成功条件和不同输入选择仍由业务回调实现。

## 构建边界

插件源码和构建文件位于 `addons/nv_timeline/native/nv_timeline/`，根 CMake 复用已有 `godot::cpp` 目标。DLL/SO 产物被 `.gitignore` 排除，提交中只保留源码、`.gdextension`、插件入口、示例和本说明；没有 Godot 编辑器可执行文件时，仍可通过 CMake 完成 C++ 编译与导出符号检查。

编辑器入口目前是一个很薄的 GDScript `EditorPlugin`，只创建独立窗口占位，不读取或修改运行时状态。后续轨道编辑器应直接操作 `NVTimelineDocument` 的 Dictionary，并继续遵守 JSON 与事件绑定分离的边界。
