# 时间轴框架技术设计

状态：历史设计初稿，部分内容已被后续讨论调整。

当前方案分为两份：

- [时间轴 JSON 表示技术方案](时间轴JSON表示技术方案.md)：定义与可视化配置对应的完整 JSON 结构。
- [时间轴事件系统技术方案](时间轴事件系统技术方案.md)：定义程序中的标签绑定、事件管理器和处理实例生命周期。

后续实现以这两份方案中的已确认约束为准。本文中的可配置时间精度、EXTERNAL 时钟、旧事件分类、JSON 业务条件和脚本绑定等内容不再作为当前方案依据。运行时与事件处理优先采用 C++，通用源码及相关文件归入独立插件目录。

适用版本：Godot 4.8

本文只描述可复用的时间轴运行时框架，不描述具体游戏剧情、AI 知识过滤、保存加载、网络同步和完整的可视化编辑器。

## 1. 目标与边界

### 1.1 目标

时间轴框架需要解决以下问题：

1. 在后台持续维护一个或多个可推进的时间轴。
2. 在一条时间轴内支持多轨道，并允许多个事件在同一时间重叠。
3. 支持瞬时触发、区间进入、区间离开、外部完成和依赖条件。
4. 允许时间轴被外部系统推进，也允许时间轴向外部系统发出事件。
5. 允许多个对等时间轴之间互相发送消息、请求推进或通知完成。
6. 让上述通信使用同一套消息协议，避免时间轴之间、时间轴与游戏系统之间出现两套不同的调用方式。
7. 将运行时核心作为独立 Godot 插件，尽量不依赖当前项目的 UI GDExtension。

### 1.2 当前阶段不处理的内容

以下内容不属于本阶段实现范围：

- AI 知识可见性和提示词过滤。
- 保存加载、版本迁移和回放文件。
- 网络同步和多人时间轴。
- 类似剪辑软件的完整编辑器 Dock。
- 复杂的动画混合、曲线插值和音视频剪辑能力。
- 当前游戏的具体剧情、角色、论坛、聊天和白板逻辑。

这些内容以后可以使用本框架的消息、条件和事件接口扩展，但不能反向污染核心运行时。

## 2. 核心设计结论

### 2.1 时间轴都是对等实例

框架不区分“全局时间轴”和“局部时间轴”，也不建立时间轴的父子关系。项目中存在的每一个时间轴都是一个对等的 `Timeline` 实例。

多个时间轴可以同时存在，并且可以有不同的用途，例如剧情进度、桌面应用状态、某个 NPC 的行为、一次临时演出或一组环境变化。它们是否共享时间，只由各自绑定的 `Clock` 决定，而不是由时间轴之间的层级决定。

时间轴之间的启动、暂停、推进、完成和通知都通过统一消息总线完成。一个时间轴可以请求另一个时间轴执行动作，但不能直接访问另一个时间轴的内部状态。

### 2.2 时钟不是时间轴

`Clock` 是独立的时间来源，负责维护逻辑时间和推进请求。`Timeline` 订阅一个时钟的推进结果，并根据自己的事件定义进行求值。

因此可以表达以下关系：

- 多个时间轴绑定同一个时钟，同时响应同一段时间推进。
- 不同时间轴绑定不同的时钟，彼此独立运行。
- 一个时间轴在运行期间更换时钟绑定，但这必须通过明确的控制命令完成。
- 外部系统只推进时钟，不直接修改时间轴当前时间。

框架中的“时间”是逻辑时间，不等同于操作系统时间。实时推进只是时钟的一种驱动模式。

### 2.3 通信只有一套语义

时间轴对外通信统一使用消息协议：

```text
外部系统  -> 消息总线 -> 时间轴
时间轴    -> 消息总线 -> 外部系统
时间轴    -> 消息总线 -> 时间轴
```

Godot Signal 可以作为消息总线的实现细节，但不能再为时间轴之间额外设计一套直接调用接口。直接调用方法只作为类型安全的便捷包装，最终仍转换为相同的消息。

## 3. 运行时模块

### 3.1 `TimelineService`

`TimelineService` 是插件提供的基础设施节点，不是时间轴本身。它负责：

- 注册和查找时间轴实例。
- 注册和管理逻辑时钟。
- 持有统一消息总线。
- 维护消息派发队列。
- 在项目退出或场景切换时停止运行时实例。

它可以作为 Autoload 使用，也可以作为场景根节点下的普通节点使用。插件不强制项目必须采用 Autoload。

### 3.2 `Clock`

`Clock` 负责维护一个单调的逻辑时间位置。当前阶段建议使用整数 tick，避免浮点数累计误差。

核心字段：

| 字段 | 含义 |
|---|---|
| `id` | 时钟的稳定标识 |
| `position` | 当前逻辑时间位置 |
| `ticks_per_second` | tick 与秒的换算比例 |
| `mode` | `MANUAL`、`REALTIME` 或 `EXTERNAL` |
| `rate` | 实时模式下的时间倍率 |
| `paused` | 是否暂停推进 |

三种驱动模式的职责如下：

- `MANUAL`：只接受 `advance_by` 或 `advance_to` 命令，适合剧情推进。
- `REALTIME`：由节点帧更新推进，适合桌面环境和持续变化的表现。
- `EXTERNAL`：由其他系统或测试驱动，适合未来接入网络或回放系统。

默认模式使用 `MANUAL`。这样玩家完成一次行动、睡到下一天或通过一个闸门时，游戏可以明确决定时间是否推进。

### 3.3 `TimelineDefinition`

`TimelineDefinition` 是可保存的 `Resource`，描述时间轴的静态结构。它不保存运行时当前位置，也不引用具体场景节点。

主要内容：

- 时间轴标识。
- 默认时长或开放式时长。
- 绑定的时钟标识。
- 轨道列表。
- 事件定义。
- 可选的标签和版本号。

资源只描述“什么时候可能发生什么”，不直接执行项目代码。具体效果由消息接收方决定。

### 3.4 `TimelineTrack`

轨道只是组织和排序单位，不代表权限、层级或互斥关系。

主要字段：

| 字段 | 含义 |
|---|---|
| `id` | 轨道标识 |
| `order` | 同时刻事件的稳定排序权重 |
| `enabled` | 是否参与求值 |
| `events` | 该轨道上的事件列表 |

同一轨道内允许事件重叠，不要求事件之间首尾相接。轨道也不自动阻止其他轨道运行。

### 3.5 `TimelineEvent`

事件是时间轴的最小调度单元。建议至少包含以下字段：

| 字段 | 含义 |
|---|---|
| `id` | 稳定且唯一的事件标识 |
| `kind` | `TRIGGER`、`INTERVAL`、`EXTERNAL` 或 `GATE` |
| `start` | 开始时间 |
| `end` | 结束时间，瞬时事件可以为空或等于 `start` |
| `channel` | 消息类型或业务频道 |
| `target` | 消息目标，可为空表示广播 |
| `payload` | 事件携带的通用数据 |
| `condition` | 进入事件前需要满足的条件 |
| `dependencies` | 依赖的事件或消息结果 |
| `late_policy` | 错过开始时间后的处理策略 |

`payload` 只传递数据，不保存对节点方法的硬编码引用。项目需要执行具体行为时，通过消息目标或接收器处理。

## 4. 时间与事件语义

### 4.1 区间定义

所有持续事件使用半开区间 `[start, end)`：

- 时间从 `start` 之前跨到 `start` 时，事件进入。
- 时间到达 `end` 时，事件离开。
- `end` 不属于事件的活跃区间。
- `start == end` 的事件是一次性触发事件。

这样可以避免相邻事件在边界处重复处于活跃状态。

### 4.2 事件生命周期

事件运行时状态统一为：

```text
PENDING -> ARMED -> ACTIVE -> COMPLETED
       \\-> BLOCKED
       \\-> SKIPPED
```

- `PENDING`：尚未到达开始时间，或依赖尚未满足。
- `ARMED`：已经满足开始条件，等待时钟跨过开始边界。
- `ACTIVE`：区间事件已经进入。
- `COMPLETED`：事件正常离开或收到外部完成消息。
- `BLOCKED`：到达边界但条件不满足，等待后续消息重新评估。
- `SKIPPED`：根据策略确认不再执行。

当前阶段保留三种 `late_policy`：

- `SKIP`：错过边界时跳过，不补发。
- `DEFER`：保留为阻塞事件，条件满足后立即触发。
- `CATCH_UP`：条件满足后补发一次，并在消息中标记为补发。

默认由事件类型决定：剧情触发建议使用 `DEFER`，纯表现事件建议使用 `SKIP`。

### 4.3 跨越多个事件

时钟一次推进可能跨过多个事件边界。播放器必须先收集区间内所有边界，再按以下排序派发：

```text
边界时间 -> 轨道 order -> 事件定义顺序 -> 事件 id
```

不能只检查推进后的当前时间，否则大步推进会漏掉中间的触发、进入和离开事件。

### 4.4 跳转与暂停

- `pause` 只停止自动推进，不清空事件状态。
- `seek` 默认只移动游标并重新计算活跃事件，不重复发送剧情消息。
- 需要逐事件回放时，调用显式的 replay 模式。
- `stop` 清理当前运行时状态并回到初始位置，但不修改资源定义。

## 5. 条件与依赖

### 5.1 条件来源

时间轴插件只定义通用条件接口，不定义游戏中的具体状态字段。条件可以读取：

- `TimelineContext` 中的布尔值、数字、字符串和标签。
- 某个事件是否已经完成。
- 某个消息是否已经收到。
- 其他系统通过消息总线发布的事实。

项目可以注册自己的条件提供器，将项目状态映射为通用条件查询，但时间轴资源本身不应该直接引用项目单例。

### 5.2 条件组合

第一阶段支持以下组合方式：

- `ALL`：所有子条件满足。
- `ANY`：任一子条件满足。
- `NOT`：子条件不满足。
- `VALUE`：比较上下文中的一个值。
- `EVENT`：比较事件生命周期状态。

条件求值必须是无副作用的。条件不能在检查时修改游戏状态，也不能触发消息。

### 5.3 外部完成

`EXTERNAL` 事件由时间轴发出开始消息，再等待外部系统发送完成命令。例如：

```text
时间轴 A 触发 task.started
外部系统完成任务
外部系统发送 event.complete，并携带 event_id
时间轴 A 将事件标记为 COMPLETED
依赖该事件的后续事件重新求值
```

外部系统不应该直接改写事件状态字段，只能发送经过校验的命令。

## 6. 统一消息协议

### 6.1 消息信封

所有消息都使用同一种结构：

| 字段 | 含义 |
|---|---|
| `type` | 消息类型，例如 `event.triggered` |
| `sender` | 发送方标识 |
| `target` | 目标标识，可为空 |
| `clock_id` | 相关时钟，可为空 |
| `timeline_id` | 相关时间轴，可为空 |
| `event_id` | 相关事件，可为空 |
| `request_id` | 请求与响应的关联标识，可为空 |
| `time` | 消息产生时的逻辑时间 |
| `payload` | 业务数据 |

消息的目标可以是某个时间轴、某个系统接收器，或广播频道。目标解析由 `TimelineService` 统一完成。

### 6.2 消息来源

三种通信都转换成同一套消息：

| 来源 | 方向 | 示例 |
|---|---|---|
| 时间轴事件 | 时间轴到系统 | `event.triggered` |
| 系统命令 | 系统到时间轴 | `timeline.advance.request` |
| 时间轴消息 | 时间轴到时间轴 | `timeline.command` |

系统可以使用 Godot Signal 监听消息，但 Signal 只是消息总线的监听表现，不改变协议和生命周期规则。

### 6.3 派发规则

- 默认使用队列派发，避免回调中再次修改当前遍历集合。
- 同一个 tick 内产生的消息按照入队顺序处理。
- 消息处理失败不能破坏时间轴游标；错误通过 `message.failed` 或运行时错误信号报告。
- 同一消息不能因为多个接收器而重复改变同一事件状态。
- 需要同步返回值的命令使用 `request_id`，普通通知不等待响应。

### 6.4 推荐的基础消息

运行时核心至少提供以下消息类型：

```text
clock.advanced
timeline.started
timeline.paused
timeline.resumed
timeline.seeked
timeline.blocked
event.entered
event.exited
event.triggered
event.completed
event.cancelled
event.complete.request
timeline.advance.request
timeline.pause.request
timeline.resume.request
timeline.seek.request
```

项目可以增加自己的消息类型，但不能绕过消息总线直接让时间轴互相持有业务对象引用。

## 7. 多时间轴协作

### 7.1 同时运行

`TimelineService` 每帧或每次外部推进时，先推进时钟，再通知绑定该时钟的所有时间轴求值。时间轴之间不按创建顺序形成隐含优先级。

同一时钟上的多个时间轴具有以下保证：

- 都收到相同的时间区间。
- 各自按照自己的事件定义求值。
- 事件消息最终进入同一个派发队列。
- 消息目标可以明确指向另一个时间轴。

### 7.2 时间轴之间通信

时间轴 A 需要影响时间轴 B 时，发送目标为 B 的命令或通知。例如：

```text
timeline_a -> timeline.command -> timeline_b
```

消息可以请求 B：

- 开始或停止。
- 推进自己的时钟。
- 触发指定事件。
- 设置一个上下文值。
- 通知某个外部任务已经完成。

B 是否接受该命令，由 B 自己根据状态和条件判断。A 不能直接修改 B 的运行时字段。

### 7.3 依赖与通信的关系

事件依赖用于表达“必须满足什么条件才能发生”；消息用于表达“某件事发生后通知谁”。两者可以组合，但不混为同一个概念：

- 依赖是可查询的状态关系。
- 消息是一次性的运行时事实。
- 一个消息可以改变上下文，使依赖重新满足。
- 一个事件可以发消息，但不能把消息接收方硬编码进条件实现。

## 8. Godot 插件边界

插件建议独立放在：

```text
addons/nv_timeline/
├── runtime/
├── resources/
├── conditions/
├── messages/
├── examples/
└── plugin.cfg
```

第一阶段使用 GDScript 实现，原因是：

- 不依赖平台二进制，方便 Godot Web 导出。
- 资源和条件迭代速度更快。
- 更容易在项目之间复制和复用。
- 与现有 `night_voyageExt` 的 C++ UI 插件解耦。

建议的运行时类型名称：

| 类型 | 职责 |
|---|---|
| `NVTimelineService` | 注册实例、时钟和消息总线 |
| `NVTimelineClock` | 维护并推进逻辑时间 |
| `NVTimelineDefinition` | 保存时间轴静态定义 |
| `NVTimelineTrack` | 保存轨道定义 |
| `NVTimelineEvent` | 保存事件定义 |
| `NVTimelineRuntime` | 执行一条时间轴 |
| `NVTimelineContext` | 提供无副作用的条件查询和运行时值 |
| `NVTimelineMessage` | 统一消息信封 |

这些类型不应依赖 `Control`、具体 UI 节点、论坛、聊天或当前项目的 `GameState`。

## 9. 第一阶段实现范围

第一阶段只实现以下内容：

1. `Clock` 的手动推进、实时推进、暂停和跳转。
2. 多个对等 `TimelineRuntime` 同时运行。
3. 多轨道和重叠事件。
4. `TRIGGER`、`INTERVAL`、`EXTERNAL` 和 `GATE` 四种事件类型。
5. 事件边界求值和稳定排序。
6. 条件组合与事件依赖。
7. 统一消息信封、消息队列和目标路由。
8. 时间轴到系统、系统到时间轴、时间轴到时间轴的统一通信。
9. 一个最小演示场景，展示两个共享时钟的时间轴和一个独立时钟的时间轴。
10. 运行时错误、重复事件和跨越多个事件边界的测试。

第一阶段不实现完整编辑器。事件资源先通过 Inspector、`.tres` 或演示场景配置，待运行时语义稳定后再制作时间轴 Dock。

## 10. 验收标准

框架完成第一阶段后，应满足以下行为：

- 两个以上时间轴可以同时运行，互不覆盖状态。
- 多个时间轴绑定同一个时钟时，收到完全一致的推进区间。
- 不同时间轴绑定不同的时钟时，可以独立推进和暂停。
- 同一时刻的多个事件全部触发，并且顺序稳定。
- 一次大步推进不会漏掉中间的触发、进入和离开事件。
- 外部系统可以完成 `EXTERNAL` 事件，并使依赖事件重新求值。
- 时间轴之间只能通过统一消息发送命令和通知。
- 回调中产生的新消息不会破坏当前事件遍历，也不会造成重复触发。
- `seek`、暂停和恢复的行为符合文档定义。
- 插件不需要引用当前项目的 UI GDExtension 就能运行。

## 11. 当前项目的接入原则

当前网页项目中的 `S.clock`、`S.day`、`sleepGate`、`when`、`need` 和 `lock` 不应在第一阶段直接搬进插件。它们属于项目领域逻辑，可以在后续通过：

- 一个手动推进的游戏时钟。
- 一个表示故事日的项目状态值。
- 项目自己的条件提供器。
- 项目自己的消息接收器。

逐步接入。这样可以保留“钟面时间”和“故事日”分离的设计，同时不把当前网页项目的状态字段变成插件公共 API。

## 12. 后续扩展方向

在第一阶段稳定后，可以在不改变核心消息语义的前提下增加：

- 保存加载和运行时快照。
- 时间轴编辑器和轨道可视化。
- AI 知识视图和角色权限过滤。
- 动画、音频和 UI 表现层适配器。
- 网络同步、回放和调试时间轴。

这些扩展应作为消息接收器、条件提供器或资源类型加入，不应修改 `Clock`、消息信封和事件边界的基本语义。
