# 时间轴框架技术设计

状态：设计方案，尚未实现。

适用版本：Godot 4.8。

本设计描述可复用的时间轴插件，包括逻辑时钟、对等时间轴、可视化编排数据、标签通信和程序事件处理。具体 JSON 字段见[时间轴 JSON 表示技术方案](时间轴JSON表示技术方案.md)，标签绑定和处理实例见[时间轴事件系统技术方案](时间轴事件系统技术方案.md)。

## 1. 目标与边界

### 1.1 目标

时间轴框架需要提供以下能力：

1. 在后台维护一条或多条可以独立运行的时间轴。
2. 支持多轨道、重叠排列和同一时间位置的多个标记。
3. 使用纯视觉事件段表达类似剪辑软件素材的时间范围。
4. 使用输出标签、阻塞输入标签和全程输入标签表达时间轴通信。
5. 在时间轴到达阻塞输入位置且尚未收到期待标签时暂停该时间轴。
6. 允许全程输入在任意时间接收标签，并由程序事件处理类决定响应。
7. 让时间轴、其他系统和其他时间轴使用同一套标签消息通信。
8. 允许项目在插件外使用 C# 继承事件处理基类，编写具体业务逻辑。
9. 将通用运行时、编辑器和脚本桥接全部封装在独立插件中。

### 1.2 本阶段边界

本阶段只定义和实现时间轴运行框架，不包含：

- 具体游戏剧情、论坛、聊天、白板和桌面应用逻辑。
- AI 知识可见性、提示词过滤和剧情防剧透。
- 游戏进度保存、运行时快照、回放文件和版本迁移。
- 网络同步和多人时间轴。
- 动画混合、曲线插值、音视频剪辑等表现能力。

这些内容可以作为插件外的标签接收方、事件处理类或后续编辑器功能接入，但不进入核心数据模型。

## 2. 核心概念

### 2.1 时间轴是对等实例

框架不区分全局时间轴和局部时间轴，也不建立时间轴父子关系。每条时间轴都是独立的对等实例。

多条时间轴可以同时存在：

- 绑定同一个时钟时，共享同一段时间推进。
- 绑定不同的时钟时，独立推进和暂停。
- 可以通过标签消息互相通知，或请求对方执行时间轴控制。

时间轴不能直接访问另一条时间轴的内部游标、输入状态或处理实例。跨时间轴操作必须通过统一消息和控制请求完成。

### 2.2 时钟

时钟是逻辑时间来源，不是时间轴本身。时钟负责维护当前位置和推进请求，时间轴订阅时钟的推进结果并求值自己的编排数据。

框架只提供两种时钟模式：

- manual：由程序提交推进请求，适合剧情、玩家行动和明确的阶段推进。
- realtime：根据实际经过的时间自动推进，适合桌面环境和持续变化的表现。

所有时间值使用固定精度：1 个时间单位等于 0.1 秒。时间轴配置中的时间、片段位置和片段长度使用非负整数；运行时用整数游标处理已完成的时间单位，并保留不足 0.1 秒的帧时间。

时钟的实时倍率只影响推进速度。时钟当前位置、暂停状态和帧累计值属于运行时状态，不写入编排 JSON。

### 2.3 可视化对象与运行时对象

时间轴 JSON 保存编辑器可以直接看到和编辑的编排对象：

| 对象 | 作用 | 是否产生业务行为 |
|---|---|---|
| 时钟定义 | 描述时间来源和驱动模式 | 由运行时推进时间 |
| 时间轴定义 | 描述一条对等时间轴的静态结构 | 由运行时创建实例 |
| 轨道 | 组织对象和显示顺序 | 不代表权限或互斥 |
| 视觉事件段 | 显示一段可拖动、可调整长度的时间范围 | 不产生业务行为 |
| 输出标签标记 | 在指定时间位置发出标签 | 通过消息总线产生通信 |
| 阻塞输入标签标记 | 在指定时间位置等待期待标签 | 影响所属时间轴的推进 |
| 全程输入标签 | 在时间轴运行期间持续接收标签 | 交给事件管理器和处理类 |

视觉事件段和程序事件处理实例使用不同术语。视觉事件段称为 TimelineClip，程序事件处理对象称为 TimelineEventHandler。两者不自动绑定。

### 2.4 文档级配置 ID

所有保存到 JSON 的配置对象共用一个文档级 id_counter。时钟、时间轴、轨道、视觉事件段、标签标记和全程输入都由程序生成 int 类型 ID。

创建对象时先让计数器自增，再检查结果：

~~~text
id_counter 自增一次
结果为负数：报错并拒绝创建
结果为非负数：将结果作为新对象 ID
~~~

实际对象 ID 从 1 开始，0 表示未分配。删除对象不回收 ID，复制或合并其他文档的对象时重新分配 ID。跨时间轴引用使用已有 ID，不重复申请。

运行时的时间轴实例 ID、事件执行 ID 和程序绑定 ID 不使用文档计数器，也不保存到 JSON。

## 3. 时间轴编排模型

### 3.1 文档

一份 .timeline.json 文件包含：

- 文档名称。
- id_counter。
- 时钟定义列表。
- 对等时间轴定义列表。

JSON 不保存事件管理器、处理类、脚本路径、方法名、对象指针、消息队列和运行时状态。所有输出标签、阻塞输入标签和全程输入标签都必须保存。

### 3.2 时间轴

时间轴定义包含：

- 程序生成的 id 和可读名称。
- clock_id，引用文档中的时钟。
- 可选的显示时长。
- 轨道列表。
- 全程输入列表。

时间轴没有预设时长时，运行直到程序停止或业务逻辑结束。不限时长不等同于循环。

### 3.3 轨道

轨道只负责组织和显示：

- 轨道数组顺序决定编辑器中的上下顺序。
- 轨道可以启用或禁用。
- 同一轨道允许多个视觉事件段重叠。
- 同一时间位置允许多个标签标记。
- 禁用轨道保留配置，但不参与运行时输出和阻塞处理。

轨道不表达权限、父子关系、互斥关系或业务优先级。

### 3.4 视觉事件段

TimelineClip 是纯视觉段落，类似剪辑软件中的素材块。它至少包含：

| 字段 | 含义 |
|---|---|
| id | 程序生成的文档级整数 ID |
| name | 编辑器显示名称 |
| start | 开始位置，单位为 0.1 秒 |
| duration | 段落长度，单位为 0.1 秒 |
| color | 编辑器显示颜色 |

片段显示范围为 [start, start + duration)。片段不填写标签、处理类、脚本、方法、条件或业务参数。

时间轴经过片段边界不会触发回调、创建处理实例或改变时间轴状态。修改片段也不会自动移动或绑定标签标记。

### 3.5 标签标记

有具体时间位置的标签标记保存在轨道的 marks 数组中，分为两类：

#### 输出标签标记

输出标记至少包含：

- id
- name
- time
- kind: output
- label

时间轴经过该位置时，运行时通过事件管理器发出 label。输出标记只表达标签，不配置目标、负载、脚本或处理类。

#### 阻塞输入标签标记

阻塞输入标记至少包含：

- id
- name
- time
- kind: blocking
- label

时间轴到达该位置时检查本次运行是否已经收到期待的标签。尚未收到时，时间轴停在该位置等待；收到后解除该标记的等待。

阻塞输入是时间轴进度控制，不会自动停止其他时间轴或共享时钟。共享时钟下单条时间轴阻塞后的游标映射和剩余推进量由运行时规则确定。

### 3.6 全程输入标签

全程输入保存在时间轴的 listeners 数组中，不填写时间位置。它至少包含：

- id
- name
- label
- enabled

全程输入在本次时间轴运行从启动到停止或完成期间有效。暂停和阻塞等待期间仍然接收标签。收到标签后，由事件管理器查找程序绑定并调用处理类；没有绑定时只记录接入诊断，不根据标签名称猜测动作。

## 4. 时间推进与标记求值

### 4.1 推进方式

时间轴不直接修改自己的时间游标。程序向时钟提交推进请求，时钟产生一个推进区间，再通知绑定该时钟的所有时间轴。

一次推进可以跨过多个时间位置。运行时必须检查区间内的所有输出标记和阻塞输入标记，不能只检查推进后的终点。

### 4.2 阻塞行为

阻塞输入只阻塞所属时间轴：

1. 时间轴求值到阻塞标记。
2. 检查本次运行已经收到的标签记录。
3. 如果匹配成功，标记通过，继续处理后续位置。
4. 如果匹配失败，时间轴进入等待状态，不处理更晚位置的标记。
5. 之后收到期待标签时，运行时解除该等待。

全程输入不参与时间位置求值，不会因为等待标签而暂停时间轴。

### 4.3 暂停、停止和跳转

- 暂停停止所属时间轴的推进，不清空接收记录和处理实例。
- 停止结束本次时间轴运行，撤销输入入口，清理接收记录，取消所属未完成处理。
- 再次运行同一份定义时创建新的运行实例，不继承旧运行状态。
- 跳转是否补发经过位置的输出标签，需要由运行时 API 明确选择普通跳转或逐标记回放模式。

这些控制请求通过事件管理器的统一队列提交，不能由业务处理类直接改写时间轴游标。

## 5. 统一标签通信

### 5.1 通信方向

所有通信都通过同一套标签消息和事件管理器：

~~~text
其他系统  -> 标签消息 -> 时间轴输入
时间轴    -> 标签消息 -> 其他系统
时间轴 A  -> 标签消息 -> 时间轴 B
事件处理类 -> 标签消息 -> 时间轴或其他系统
~~~

Godot Signal 可以作为监听表现或桥接实现，但不能形成绕过事件管理器的第二套业务通信语义。

### 5.2 消息内容

标签消息在内存中可以附带管理所需的运行信息：

| 信息 | 用途 |
|---|---|
| 标签 | 输入匹配和业务识别 |
| 来源 | 区分时间轴、运行实例或其他系统 |
| 目标 | 路由到时间轴、系统接收器或广播 |
| 时间轴运行 ID | 关联某次运行 |
| 输入入口 ID | 定位阻塞标记或全程输入 |
| 事件执行 ID | 关联异步完成、失败和取消 |
| 当前逻辑时间 | 记录消息发生位置 |

这些字段是运行时上下文，不写回编排 JSON。JSON 中的输出配置仍然只有标签。

### 5.3 消息队列

事件管理器统一维护消息队列：

- 标签和时间轴控制请求都进入队列。
- 回调中产生的新消息在当前派发轮次之后处理。
- 同一派发轮次内按入队顺序处理。
- 消息失败记录诊断，不破坏时间轴游标。
- 需要限制单轮消息数量，防止标签互相触发形成无限循环。

广播、指定接收方和同标签多个输入的完整路由规则由事件系统实现，但不新增 JSON 业务字段。

## 6. 事件管理器与处理类

### 6.1 事件管理器

NVTimelineEventManager 随 NVTimelineService 创建，服务于该系统内的全部时钟和对等时间轴。它负责：

- 注册标签目录和程序绑定。
- 判断时间轴输入入口是否有效。
- 维护统一标签与控制请求队列。
- 按绑定创建处理实例。
- 调用处理实例的执行、完成、失败和取消入口。
- 管理执行 ID、对象引用、异步回调和清理。
- 在时间轴停止或系统销毁时撤销输入和处理实例。

管理器不负责修改 JSON，不创建视觉事件段，也不把处理类写入时间轴配置。

### 6.2 C++ 核心

以下部分使用 C++ 实现：

- NVTimelineService。
- 时钟和时间推进。
- 时间轴运行时和阻塞求值。
- 轨道、片段和标签标记的通用数据模型。
- JSON 解析、校验和写回。
- NVTimelineEventManager。
- 消息队列、路由和运行时状态。
- 脚本桥接所需的原生上下文。

C++ 负责性能、生命周期和跨时间轴一致性，不要求项目为每个业务事件编写原生扩展。

### 6.3 C# 事件处理基类

插件提供 TimelineEventHandler C# 基类，建议继承 Godot 的 RefCounted。项目在插件目录外继承它，编写具体业务事件。

基类契约包括：

- Execute(context)：开始处理一次有效标签。
- Cancel()：取消本次处理并释放业务回调。
- context.PublishLabel(...)：提交后续标签。
- context.PauseTimeline()、context.StopTimeline()：提交控制请求。
- context.Complete()、context.Fail(...)：报告本次处理终态。

C# 类不直接修改 C++ 时间轴对象，也不直接持有其他时间轴内部状态。

### 6.4 脚本桥接

C++ 管理器通过桥接层调用项目的 C# 事件：

1. C# 注册包装层登记标签与实例工厂。
2. C++ 管理器收到有效输入后调用工厂，创建 RefCounted 处理对象。
3. 桥接层包装原生上下文并调用 Execute。
4. C# 事件通过上下文提交标签、控制请求或完成状态。
5. 管理器按执行 ID 更新生命周期并清理引用。

桥接使用 Godot 支持的对象、RefCounted、Callable 和基本类型。C# 与 GDScript 不能互相继承脚本基类；如提供 GDScript 入口，则使用独立基类和同一套 C++ 管理器规则。

### 6.5 处理实例生命周期

处理实例的状态由 C++ 管理器维护：

~~~text
Created -> Running -> Completed -> Released
                    -> Failed    -> Released
                    -> Cancelled -> Released
~~~

同步处理和异步处理都必须报告终态。重复完成、取消后完成和停止后的迟到回调不能重新激活执行。

管理器在执行期间保持处理对象和回调有效；进入终态后清理业务回调、原生引用和托管引用。C# 垃圾回收不能替代管理器的取消和释放流程。

处理实例完成不自动等于阻塞输入通过。业务处理需要发出期待的完成标签，阻塞标记再按自己的输入规则通过。

## 7. 多时间轴协作

### 7.1 共享时钟

同一时钟绑定的时间轴收到同一个推进区间，各自独立求值：

- 一条时间轴阻塞不会自动停止其他时间轴。
- 各条时间轴维护自己的游标、阻塞状态和输入记录。
- 所有输出标签进入同一个事件管理器队列。
- 同一时间位置的处理顺序由运行时稳定规则决定，不依赖时间轴创建顺序。

### 7.2 独立时钟

不同时间轴绑定不同的时钟，可以独立推进、暂停和停止。事件管理器仍然统一接收和路由它们产生的标签。

### 7.3 时间轴间控制

时间轴可以通过标签或控制请求通知另一条时间轴：

- 启动、暂停、恢复或停止。
- 请求推进其绑定的时钟。
- 通知某个标签已经发生。
- 请求另一条时间轴重新评估输入。

目标时间轴决定是否接受请求。发送方不能直接修改目标时间轴的运行时字段。

## 8. 插件边界

通用实现全部归属于 addons/nv_timeline/：

~~~text
addons/nv_timeline/
├── runtime/       # C++ 时间轴、时钟和事件管理器
├── resources/     # 通用编排数据和 JSON 支持
├── editor/        # 可视化编辑器
├── csharp/        # C# 基类、注册包装和上下文包装
├── script/        # 可选 GDScript 接入
├── messages/      # 标签消息和路由支持
├── examples/      # 插件通用示例
├── native/        # 插件自己的原生源码与构建产物
└── plugin.cfg
~~~

插件不依赖当前项目的 UI GDExtension、游戏单例、场景节点路径或业务数据结构。项目派生事件类、标签绑定和具体处理逻辑放在使用方项目中。

插件可以作为 Autoload 使用，也可以作为普通场景节点使用。是否使用 Autoload 由项目决定。

## 9. 第一阶段实现范围

第一阶段包含：

1. manual 和 realtime 两种时钟模式。
2. 固定 0.1 秒时间单位和整数游标。
3. 多个对等时间轴及共享或独立时钟。
4. 多轨道、重叠视觉事件段和同位置多标记。
5. 输出标签标记、阻塞输入标签标记和全程输入标签。
6. JSON 文档级 id_counter 和 int ID 分配、加载、保存与校验。
7. 标签消息、时间轴控制请求、消息队列和基础路由。
8. 事件管理器的程序绑定和处理实例生命周期。
9. C# 事件处理基类、注册包装和 C++ 桥接原型。
10. 必要的运行时错误、重复终态、跨多个标记推进和停止清理测试。
11. 可编辑的时间轴界面，包括轨道、事件段、标签标记和全程输入区域。

本阶段不实现完整的业务事件库、保存加载进度、AI 扩展和网络同步。

## 10. 验收标准

框架完成第一阶段后，应满足：

- 多条时间轴可以同时运行，互不覆盖自己的游标和输入状态。
- 共享时钟的时间轴收到同一段推进，独立时钟可以单独推进和暂停。
- 同一轨道和不同轨道中的视觉事件段可以重叠，并且只影响编辑器显示。
- 同一时间位置的多个输出标签都能发出，顺序稳定。
- 一次大步推进不会漏掉中间的输出或阻塞位置。
- 阻塞输入未收到期待标签时，所属时间轴停在该位置。
- 收到期待标签后，阻塞输入可以解除等待；其他时间轴不被连带停止。
- 全程输入在运行、暂停和阻塞等待期间都能按配置接收标签。
- 输出、系统输入和时间轴间通信都经过同一个事件管理器和消息队列。
- 程序可以在插件外继承 C# 基类并注册标签绑定。
- C# 同步和异步处理都能完成、失败、取消并正确释放引用。
- 停止和重新运行后，旧执行和迟到回调不能影响新运行。
- 所有保存到 JSON 的配置对象 ID 在单份文档内唯一，删除后不重复使用。
- 编辑器修改视觉事件段不会创建或修改业务处理实例。
- 插件通用源码和构建产物均位于插件目录。

## 11. 当前项目接入原则

当前网页项目中的时钟、故事日、睡眠闸门、条件函数和状态锁属于项目领域逻辑，不直接成为插件公共 API。

接入时由项目完成：

- 创建和推进自己的手动时钟。
- 用项目状态维护故事日等领域数据。
- 注册项目标签目录和标签处理绑定。
- 在项目代码中实现 C# 事件处理类。
- 将论坛、聊天、白板和桌面 UI 作为标签接收方或处理实例接入。

插件只提供时间、标签、输入有效性、事件管理和生命周期能力。项目可以在不修改插件核心的情况下替换自己的业务处理。

## 12. 后续扩展方向

在第一阶段稳定后，可以增加：

- 运行时快照、保存加载和版本迁移。
- 更完整的时间轴编辑器、复制粘贴和导入导出。
- AI 知识视图、角色权限和信息过滤。
- 动画、音频、UI 表现适配器。
- 网络同步、回放和调试时间轴。

这些扩展应作为编辑器能力、标签接收方、事件处理类或独立适配器加入，不改变时钟、标签输入输出、文档 ID 分配和事件管理器的基本边界。
