# 时间轴框架技术设计

状态：C++ 运行时、统一请求队列和首版 JSON 编辑器已实现。业务回调使用 Callable，由项目自行管理异步工作；插件仅等待输出标记的成功/失败结果。多文件时间轴协作列为后续扩展，当前暂缓。

适用版本：Godot 4.8。

本设计描述可复用的时间轴插件，包括逻辑时钟、时间轴编排数据、标签通信和项目业务 Callable。具体 JSON 字段见[时间轴 JSON 表示技术方案](时间轴JSON表示技术方案.md)，标签绑定和输出结果等待见[时间轴事件系统技术方案](时间轴事件系统技术方案.md)。

## 1. 目标与边界

### 1.1 目标

时间轴框架需要提供以下能力：

1. 在后台维护可以独立运行的时间轴；每个 `.timeline.json` 文件只编排一条时间轴。
2. 支持多轨道、每条轨道内按时间顺序排列的视觉片段，以及同一时间位置的多个标记。
3. 使用纯视觉事件段表达类似剪辑软件素材的时间范围。
4. 使用输出标签、阻塞输入标签和全程输入标签表达时间轴通信。
5. 在时间轴到达阻塞输入位置且尚未收到期待标签时暂停该时间轴。
6. 允许全程输入在任意时间接收标签，并由项目注册的 Callable 决定响应。
7. 让时间轴、其他系统和其他时间轴使用同一套标签消息通信。
8. 允许项目通过 Godot Callable 接入自己的业务回调，并由项目代码管理异步业务过程。
9. 将通用运行时、编辑器和 Godot Callable 接口全部封装在独立插件中。

### 1.2 本阶段边界

本阶段只定义和实现时间轴运行框架，不包含：

- 具体游戏剧情、论坛、聊天、白板和桌面应用逻辑。
- AI 知识可见性、提示词过滤和剧情防剧透。
- 游戏进度保存、运行时快照、回放文件和版本迁移。
- 网络同步和多人时间轴。
- 动画混合、曲线插值、音视频剪辑等表现能力。

这些内容可以由插件外的 Callable、标签接收方或后续编辑器功能接入，但不进入核心数据模型。

## 2. 核心概念

### 2.1 时间轴是对等实例

框架不区分全局时间轴和局部时间轴，也不建立时间轴父子关系。时间轴在概念上是对等实例，但当前一个 JSON 文档只包含一条时间轴，Service 当前只装入一份文档，因此多时间轴协作暂未实现。

多文件同时装入、共享时钟以及时间轴间标签和控制请求属于后续扩展。届时仍应通过统一请求通信，不能直接访问另一条时间轴的游标或输入状态。

### 2.2 时钟

时钟是逻辑时间来源，不是时间轴本身。时钟负责维护当前位置和推进请求，时间轴订阅时钟的推进结果并求值自己的编排数据。

框架只提供两种时钟模式：

- manual：由程序提交推进请求，适合剧情、玩家行动和明确的阶段推进。
- realtime：根据实际经过的时间自动推进，适合桌面环境和持续变化的表现。

所有时间值使用固定精度：1 个时间单位等于 0.1 秒。时间轴配置中的时间、片段位置和片段长度使用非负整数；运行时用整数游标处理已完成的时间单位，并保留不足 0.1 秒的帧时间。

时钟的实时倍率只影响推进速度。时钟当前位置、暂停状态和帧累计值属于运行时状态，不写入编排 JSON。

### 2.3 可视化对象与运行时对象

时间轴 JSON 保存编辑器可以直接看到和编辑的编排对象：

| 对象 | 作用 | 是否产生业务行为 |
|---|---|---|
| 时钟定义 | 描述时间来源和驱动模式 | 由运行时推进时间 |
| 时间轴定义 | 描述一条对等时间轴的静态结构 | 由运行时创建实例 |
| 轨道 | 组织对象和显示顺序 | 不代表权限或互斥 |
| 视觉事件段 | 显示一段可拖动、可调整长度的时间范围 | 不产生业务行为 |
| 输出标签标记 | 在指定时间位置发出标签；可选等待业务成功或失败 | 通过消息总线产生通信，也可阻塞所属时间轴 |
| 阻塞输入标签标记 | 在指定时间位置等待期待标签 | 影响所属时间轴的推进 |
| 全程输入标签 | 在时间轴运行期间持续接收标签 | 交给事件管理器和项目 Callable |

视觉事件段称为 TimelineClip；业务逻辑由项目 Callable 承接。两者不自动绑定，经过片段边界不会触发 Callable。

### 2.4 文档级配置 ID

所有保存到 JSON 的配置对象共用一个文档级 id_counter。时钟、时间轴、轨道、视觉事件段、标签标记和全程输入都由程序生成 int 类型 ID。

创建对象时先让计数器自增，再检查结果：

~~~text
id_counter 自增一次
结果为负数：报错并拒绝创建
结果为非负数：将结果作为新对象 ID
~~~

实际对象 ID 从 1 开始，0 表示未分配。删除对象不回收 ID，复制或合并其他文档的对象时重新分配 ID。跨时间轴引用使用已有 ID，不重复申请。

运行时的时间轴运行 ID 和程序绑定 ID 不使用文档计数器，也不保存到 JSON。当前插件不创建业务事件执行实例。

## 3. 时间轴编排模型

### 3.1 文档

一份 .timeline.json 文件包含：

- 文档名称。
- id_counter。
- 时钟定义列表。
- 唯一的时间轴定义。

JSON 不保存事件管理器、Callable 绑定、脚本路径、方法名、对象指针、消息队列和运行时状态。所有输出标签、阻塞输入标签和全程输入标签都必须保存。

### 3.2 时间轴

时间轴定义包含：

- 程序生成的 id 和可读名称。
- clock_id，引用文档中的时钟。
- 可选的显示时长。
- 轨道列表。
- 全程输入列表。

时间轴没有预设时长时，运行直到程序停止或业务逻辑结束。不限时长不等同于循环。

### 3.3 轨道

轨道只负责组织和显示：

- 轨道数组顺序决定编辑器中的上下顺序。
- 轨道可以启用或禁用。
- 同一轨道内的视觉事件段不得重叠，但可以与标签标记处于同一时间位置；需要并行表现时应使用不同轨道。
- 同一时间位置允许多个标签标记。
- 禁用轨道保留配置，但不参与运行时输出和阻塞处理。

轨道不表达权限、父子关系、互斥关系或业务优先级。

### 3.4 视觉事件段

TimelineClip 是纯视觉段落，类似剪辑软件中的素材块。它至少包含：

| 字段 | 含义 |
|---|---|
| id | 程序生成的文档级整数 ID |
| name | 编辑器显示名称 |
| start | 开始位置，单位为 0.1 秒 |
| duration | 段落长度，单位为 0.1 秒 |
| color | 编辑器显示颜色 |

片段显示范围为 [start, start + duration)。片段不填写标签、处理类、脚本、方法、条件或业务参数。

时间轴经过片段边界不会触发回调、创建业务处理对象或改变时间轴状态。修改片段也不会自动移动或绑定标签标记。

### 3.5 标签标记

有具体时间位置的标签标记保存在轨道的 marks 数组中，分为两类：

#### 输出标签标记

输出标记至少包含：

- id
- name
- time
- kind: output
- label
- 可选 wait_for_result，默认 false

时间轴经过该位置时，运行时通过事件管理器发出 label。默认不等待，设置 wait_for_result 后会停在该标记，等待项目 Callable 提交成功或失败。输出标记不配置目标、负载、脚本或处理类。

#### 阻塞输入标签标记

阻塞输入标记至少包含：

- id
- name
- time
- kind: blocking
- label

时间轴到达该位置时检查本次运行是否已经收到期待的标签。尚未收到时，时间轴停在该位置等待；收到后解除该标记的等待。

阻塞输入是时间轴进度控制，不会自动停止共享时钟。普通推进遇阻时丢弃本次剩余推进量；显式快进会保留目标，解除阻塞后继续到目标。

### 3.6 全程输入标签

全程输入保存在时间轴的 listeners 数组中，不填写时间位置。它至少包含：

- id
- name
- label
- enabled

全程输入在本次时间轴运行从启动到停止或完成期间有效。暂停和阻塞等待期间仍然接收标签。收到标签后，由事件管理器查找项目 Callable 并调用；没有绑定时只记录接入诊断，不根据标签名称猜测动作。

## 4. 时间推进与标记求值

### 4.1 推进方式

时间轴不直接修改自己的时间游标。程序向 Service 提交时钟推进请求，Service 推进对应时钟，再让绑定该时钟的时间轴求值。

一次推进可以跨过多个时间位置。运行时必须检查区间内的所有输出标记和阻塞输入标记，不能只检查推进后的终点。

### 4.2 阻塞行为

阻塞输入只阻塞所属时间轴：

1. 时间轴求值到阻塞标记。
2. 检查本次运行已经收到的标签记录。
3. 如果匹配成功，标记通过，继续处理后续位置。
4. 如果匹配失败，时间轴进入等待状态，不处理更晚位置的标记。
5. 之后收到期待标签时，运行时解除该等待。

全程输入不参与时间位置求值，不会因为等待标签而暂停时间轴。

`output.wait_for_result` 是另一种阻塞：标签已经发出，时间轴等待项目 Callable 返回成功或失败。成功继续，失败停止本次运行。插件只校验时间轴 ID、运行 ID 和标记 ID，不追踪项目异步过程。

### 4.3 暂停、停止和跳转

- 暂停停止所属时间轴的推进，不清空接收记录；等待中的输入仍可到达。
- 停止结束本次时间轴运行并清理接收记录。插件没有需要取消的业务处理实例。
- 再次运行同一份定义时产生新的运行 ID，不继承旧运行状态；旧输出结果会被拒绝。
- `fast_forward` 按序求值并触发期间标记，遇到阻塞时保留目标。
- `jump` 只允许向前，直接略过目标位置及之前的标记，不发标签也不等待阻塞。

回调中的标签、控制、快进、跳转和结果请求通过 `NVTimelineService.submit_request` 进入同一 FIFO 队列。原有便捷控制方法保留兼容；回调内应使用统一请求入口。

## 5. 统一标签通信

### 5.1 通信方向

所有通信都通过同一套标签消息和事件管理器：

~~~text
其他系统  -> 标签消息 -> 时间轴输入
时间轴    -> 标签消息 -> 其他系统
时间轴 A  -> 标签消息 -> 时间轴 B
项目 Callable -> 标签消息 -> 时间轴或其他系统
~~~

Godot Signal 可以作为监听表现或桥接实现，但不能形成绕过事件管理器的第二套业务通信语义。

### 5.2 消息内容

标签消息在内存中可以附带管理所需的运行信息：

| 信息 | 用途 |
|---|---|
| 标签 | 输入匹配和业务识别 |
| 来源 | 区分时间轴、运行实例或其他系统 |
| 目标 | 路由到时间轴、系统接收器或广播 |
| 时间轴运行 ID | 关联某次运行 |
| 输入入口 ID | 定位阻塞标记或全程输入 |
| 输出标记 ID | 将等待结果关联到触发它的标记 |
| 当前逻辑时间 | 记录消息发生位置 |
| wait_for_result | 告知项目回调是否需要提交结果 |

这些字段是运行时上下文，不写回编排 JSON。JSON 中的输出配置仍然只有标签。

### 5.3 消息队列

事件管理器与 Service 共用 FIFO 请求队列。九类公开请求为：`publish_label`、`start_timeline`、`pause_timeline`、`resume_timeline`、`stop_timeline`、`advance_clock`、`fast_forward`、`jump` 和 `resolve_output_result`。运行时输出生成的 `label` 是内部消息类型，不属于公开请求。

回调中产生的新请求排到当前请求之后，同一派发轮次依入队顺序处理；单轮默认最多处理 1024 条，避免循环触发。标签默认广播，也可以指定目标时间轴。更详细的字段和示例见[时间轴运行时实现说明](时间轴运行时实现说明.md)。

## 6. 事件管理器与项目 Callable

### 6.1 事件管理器

`NVTimelineEventManager` 随 `NVTimelineService` 创建，负责保存标签到 `Callable` 的绑定、接收统一 FIFO 队列中的请求，并把有效标签上下文交给对应回调。它不创建或持有业务处理对象，也不追踪项目异步工作的步骤、用时和取消过程。

标签输入只有在至少一个运行中的时间轴接受了对应入口时，才会被要求“必须匹配时间轴输入”的绑定处理。普通绑定仍可接收任意同名标签。时间轴输入的有效性、标签路由和业务 Callable 调用由 C++ 实现。

### 6.2 统一请求入口

项目代码通过 `NVTimelineService.submit_request(Dictionary)` 提交业务请求。该函数接受九种类型：

1. `publish_label`：发出标签，可选指定目标时间轴。
2. `start_timeline`：启动时间轴。
3. `pause_timeline`：暂停时间轴。
4. `resume_timeline`：恢复时间轴。
5. `stop_timeline`：停止时间轴。
6. `advance_clock`：按 0.1 秒单位推进时钟。
7. `fast_forward`：按序求值至绝对位置，遇阻保留目标。
8. `jump`：向前直接跳转，略过目标位置及之前的标记。
9. `resolve_output_result`：为等待结果的输出提交成功或失败。

请求先按 FIFO 顺序排队，回调中追加的请求不会递归改写正在派发的时间轴状态。旧的 Service 便捷控制方法为兼容保留；回调中应使用 `submit_request`。

### 6.3 等待业务结果

输出标记的 `wait_for_result` 默认是 `false`。普通输出只发出标签；设置为 `true` 时，时间轴停在该标记，回调收到包含时间轴 ID、运行 ID、标记 ID 和 `wait_for_result` 的 Dictionary 上下文。

项目 Callable 自行管理 UI、玩家输入或其他异步逻辑。完成后以 `resolve_output_result` 提交 `success: true` 或 `success: false`。成功继续时间轴，失败停止当前运行。插件校验时间轴运行 ID 和标记 ID；业务分支和值的含义由项目代码通过其他标签表达。

## 7. 多时间轴协作（后续扩展）

当前一个 Service 只加载一个 JSON 文档，而一个文档只包含一条时间轴，因此同一 Service 内的多时间轴协作暂未实现。

后续若支持多个文档同时运行，时间轴之间可以共享或分别绑定时钟，并通过统一标签队列通信。一条时间轴阻塞时不应自动停止其他时间轴；发送方也不能直接修改接收方的游标、阻塞或输入状态。多文档加载顺序、ID 作用域和卸载规则需要在该扩展开始前另行确定。

## 8. 插件边界

通用实现全部归属于 addons/nv_timeline/：

~~~text
addons/nv_timeline/
├── editor/        # Godot 编辑器插件入口
├── examples/      # 插件通用时间轴示例
├── native/        # C++ 运行时、编辑器控件与构建文件
├── bin/           # 构建生成的原生扩展
├── nv_timeline.gdextension
└── plugin.cfg
~~~

插件不依赖当前项目的 UI GDExtension、游戏单例、场景节点路径或业务数据结构。项目的标签绑定、Callable 和具体异步处理逻辑放在使用方项目中。

插件可以作为 Autoload 使用，也可以作为普通场景节点使用。是否使用 Autoload 由项目决定。

## 9. 可视化编辑器窗口

时间轴插件的编辑界面采用类似 Unity 插件窗口的独立弹出界面，不以内嵌 Dock 作为主要工作区域。用户在 Godot 编辑器中点击插件入口后，打开一个非模态的时间轴编辑窗口；该窗口可以独立移动、调整大小，并与 Godot 主编辑器同时存在。

独立窗口至少包含：

- 时间轴文档和当前时间轴属性。
- 时钟、轨道、视觉事件段、输出标签标记、阻塞输入标记和全程输入的可视化编辑。
- 时间刻度、缩放、滚动和播放位置。
- 对象属性、标签选择和 JSON 文件保存。
- 只读的程序标签目录与绑定诊断。

窗口编辑的数据直接对应 JSON 编排结构。窗口关闭或切换文档时，编辑器应先处理未保存修改；窗口布局、停靠位置、滚动位置和临时选中项属于编辑器会话状态，不写入时间轴 JSON。

该窗口是编辑器工具，不是游戏运行时界面。打开、关闭或移动窗口不会启动、暂停或修改时间轴运行实例；运行时调试显示属于后续功能。

实现上由 Godot EditorPlugin 提供菜单或工具栏入口，并创建独立的 Window。窗口内部可以使用 C++ 编辑器控件，必要的脚本胶水不改变 JSON 和事件系统的边界。

## 10. 当前项目接入原则

当前网页项目中的时钟、故事日、睡眠闸门、条件函数和状态锁属于项目领域逻辑，不直接成为插件公共 API。

接入时由项目完成：

- 通过 `submit_request` 启动时间轴、推进手动时钟并提交标签。
- 用项目状态维护故事日等领域数据。
- 注册项目标签到 Callable 的绑定。
- 在业务 Callable 中实现论坛、聊天、白板、桌面 UI 和异步玩家交互。
- 需要多个业务分支时，由 Callable 按业务结果发出不同输入标签。

插件只提供时间轴推进、标签路由、输入有效性、统一请求队列和等待结果校验。项目可以在不修改插件核心的情况下替换自己的业务逻辑。
