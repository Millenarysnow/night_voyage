# 时间轴运行时实现说明

这份说明记录 `addons/nv_timeline/` 当前第一版实现与设计稿的对应关系。它只描述已经落地的运行时行为，编辑器的完整轨道控件和跨语言事件实例生命周期仍可在此基础上继续扩展。

## 已实现的 C++ 类型

- `NVTimelineDocument`：读取/保存 `.timeline.json`，执行字段白名单、类型、ID 唯一性、时钟引用、时间范围、标签和颜色校验。
- `NVTimelineClock`：维护 0.1 秒整数时间单位；`manual` 由 `advance_units` 推进，`realtime` 在 Service 的 `_process` 中累计实际秒数和倍率。
- `NVTimelineRuntime`：把启用轨道中的 marks 展平为稳定顺序，维护运行 ID、游标、暂停、完成和阻塞等待状态。
- `NVTimelineEventManager`：维护 FIFO 标签队列和 Godot `Callable` 绑定；回调收到统一 Dictionary 上下文。
- `NVTimelineService`：持有全部时钟、平级时间轴和唯一事件管理器，负责实时驱动、标签路由、诊断信号和运行控制。

## 首版调度规则

设计稿中列出的未定调度细节在第一版采用以下确定规则：

1. 同一时间点按 `tracks` 数组顺序，再按 `marks` 数组顺序求值。
2. 一次推进会检查区间内全部标记；遇到未满足的阻塞标记时，所属时间轴停在该位置，不处理更晚标记。
3. 阻塞点截断本次推进，未使用的单位不追赶；共享时钟继续推进，其他时间轴不受影响。
4. 同一个标签可以同时记录到一条时间轴的多个阻塞标记和全程输入。
5. 时间轴暂停时全程输入和阻塞输入仍接收标签；如果暂停同时覆盖等待状态，收到标签只解除等待，恢复请求仍需由程序提交。
6. 输出和回调中新发的标签进入同一队列尾部；单轮最多派发 1024 条，超过上限会记录诊断并留到下一帧。
7. 时间为 0 的输出标记在 `start_timeline` 时求值；有限时长到达末端且没有未完成标记时发出 `timeline_completed`。

这些规则属于运行时实现，不会增加 JSON 字段；未来若需要改变，应该通过 API 或版本说明调整，而不是把事件处理逻辑写进编排文件。

## Godot 使用入口

构建根项目后，将 `res://addons/nv_timeline/nv_timeline.gdextension` 保持在项目目录中即可加载原生类。典型调用顺序如下：

```gdscript
var service := NVTimelineService.new()
add_child(service)
service.load_json_file("res://addons/nv_timeline/examples/basic.timeline.json")
service.start_timeline(2)
service.advance_clock(1, 10)
service.publish_label("demo_confirmed")
```

业务代码通过 `service.get_event_manager().register_binding(label, callable, requires_timeline_input)` 登记处理回调。回调上下文包含 `label`、来源时间轴和运行 ID、逻辑时间、已接收时间轴 ID 与输入 ID；这些运行信息不会写回 JSON。当前第一版先以 Godot `Callable` 作为 C# / GDScript 的兼容边界，尚未把设计稿中的 `TimelineEventHandler` 托管生命周期包装写入插件，避免在未验证的 .NET 工厂签名上固化 API。

## 构建边界

插件源码和构建文件位于 `addons/nv_timeline/native/nv_timeline/`，根 CMake 复用已有 `godot::cpp` 目标。DLL/SO 产物被 `.gitignore` 排除，提交中只保留源码、`.gdextension`、插件入口、示例和本说明；没有 Godot 编辑器可执行文件时，仍可通过 CMake 完成 C++ 编译与导出符号检查。

编辑器入口目前是一个很薄的 GDScript `EditorPlugin`，只创建独立窗口占位，不读取或修改运行时状态。后续轨道编辑器应直接操作 `NVTimelineDocument` 的 Dictionary，并继续遵守 JSON 与事件绑定分离的边界。
