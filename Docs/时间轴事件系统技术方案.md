# 时间轴事件系统技术方案

状态：C++ 标签路由、Callable 接入、统一请求队列和输出成功/失败等待已实现；业务回调的异步过程及处理对象生命周期由项目自行管理。

关联文档：[时间轴 JSON 表示技术方案](时间轴JSON表示技术方案.md)。

## 1. 已确认的设计约束

事件系统由程序实现。标签与处理类的绑定不在可视化编辑器中编辑，也不写入 JSON。

时间轴系统持有事件管理器。管理器负责标签绑定、消息排队和标签路由，随所属时间轴系统创建和销毁；业务处理对象及其异步生命周期由项目管理。

### 当前实现口径

当前实现不创建 `TimelineEventHandler` 对象，也不跟踪业务回调的运行时长、异步步骤或取消流程。注册绑定仍是标签到 `Callable` 的映射。输出标记可以选择等待一个成功/失败结果；项目回调自行保存上下文，并通过统一请求提交结果。插件只校验该结果是否仍对应当前时间轴运行和输出标记。

因此，本方案后文关于处理实例工厂、插件持有脚本对象、完成/失败/取消生命周期和 C# 基类的内容属于早期备选设计，不属于当前实现要求。多文件在同一 Service 中加载也记录为后续扩展，当前暂缓。

已确认的边界：

- JSON 完整保存输出标签、阻塞输入标签和全程输入标签，但不保存事件执行系统。
- 普通输出标记只发出标签；`wait_for_result: true` 的输出还会等待业务回调返回成功或失败。
- 阻塞输入具有时间点；到达时间点而尚未收到期待的标签时，时间轴等待。
- 全程输入没有具体时间点，等待消息期间不阻塞时间轴。
- 可视化中的“事件段”是纯视觉 TimelineClip，进入 JSON，但不属于本事件执行系统。
- 具体处理逻辑由项目注册的 Callable 承接；异步业务工作由项目自行管理。
- 时间轴到其他系统、其他系统到时间轴、时间轴到时间轴使用同一套标签通信机制。
- 多个时间轴对等，可同时运行，不建立“全局／局部”或父子层级。
- 标签、控制、快进、跳转和输出结果使用 Service 的同一请求队列。
- C++ 负责时间轴游标和输出等待结果校验，不负责业务处理对象的持有、计时或取消。
- 多文件在同一 Service 中加载暂列为后续扩展，当前暂缓。

类型名称、接口名称、实例创建策略和下文的工程规则为实现建议。未确定的调度行为集中列在最后一节。

## 2. 核心概念

### 2.1 标签

标签是通信的匹配标识，例如 puzzle_start、puzzle_completed、urgent_interrupt。

标签本身不代表处理类，不携带 JSON 脚本配置，也不等同于事件实例。相同标签可以被不同接收方使用。

输出和输入以每条时间轴的视角定义。一条时间轴发出的输出标签，可以成为另一条时间轴的输入标签，也可以由其他系统接收。

### 2.2 时间轴输入入口

时间轴输入入口分为两种：

| 入口 | 接收规则 | 运行时职责 |
|---|---|---|
| 阻塞标记 | 与某个时间位置关联，等待期待的标签 | 保存本次运行的接收结果；到达位置时检查；必要时等待 |
| 全程输入 | 本次运行有效期内持续接收标签 | 收到标签后，将有效输入交给事件管理器 |

输入入口声明与其标签都由 JSON 保存。框架的等待和解除等待逻辑不需要额外业务处理类。

### 2.3 程序绑定

程序绑定描述“某个接收方收到某个标签时，调用哪个项目 Callable”。

绑定由代码注册。项目可以在 Callable 中调用业务类、管理其异步操作并保存所需上下文；这些代码和依赖均不进入编排 JSON。

### 2.4 业务异步处理

插件不创建业务处理实例。Callable 可以即时完成，也可以把运行上下文保存到项目对象中，等待界面交互或其他系统的异步结果。

如果对应输出标记设置 `wait_for_result`，时间轴会停在该标记。项目回调完成后，通过 `resolve_output_result` 提交成功或失败；成功继续，失败停止本次运行。插件只验证返回的时间轴运行 ID 和标记 ID 是否仍有效。

### 2.5 纯视觉事件段

编辑器中的“事件段”在程序中称为 TimelineClip，用开始位置、长度、名称和颜色表达一段可视化内容，保存于 JSON 的轨道 clips 数组。

TimelineClip 与事件处理实例之间不建立自动关系。经过片段边界不创建或结束处理实例，处理实例结束也不自动修改片段长度或颜色。

片段、输出标记和阻塞标记可以显示在同一轨道。事件管理器只处理标签和业务执行，不把片段解释为可执行事件。

## 3. 系统结构与职责

建议沿用 NVTimelineService 作为时间轴系统的基础设施节点。它可以是场景中的普通节点，也可以由项目作为 Autoload 使用。

一个 Service 持有一个事件管理器，服务于它管理的所有时钟和对等时间轴。每条时间轴不再各自创建一套事件管理器。

~~~mermaid
flowchart TB
    S["时间轴系统 NVTimelineService"]
    C["时钟与时间轴运行时"]
    M["事件管理器 NVTimelineEventManager"]
    R["程序注册的标签绑定"]
    S --> C
    S --> M
    M --> R
    C -->|"发出标签／提交有效输入"| M
    M -->|"按标签调用"| R
    R -->|"提交标签／控制／结果请求"| M
~~~

| 类型 | 建议职责 |
|---|---|
| NVTimelineService | 持有时钟、时间轴运行实例和事件管理器；管理系统启动与退出 |
| NVTimelineRuntime | 求值时间标记；维护输入入口、接收记录、阻塞和暂停状态 |
| NVTimelineEventManager | 维护代码绑定与统一请求队列，并向 Callable 发送标签上下文 |
| 项目 Callable | 执行业务逻辑；需要异步工作时由项目保存和清理自己的业务状态 |
| 统一请求 Dictionary | 保存请求类型、目标、来源、逻辑时间或输出结果等运行时字段 |

标签通信队列由事件管理器维护，Service 使用该管理器，不另建第二条独立业务通信通道。Godot Signal 可用于接入回调或显示诊断，最终仍走统一通信入口。

时间轴运行时负责“何时发出、何时等待”，管理器负责“按顺序路由哪个请求”，项目 Callable 负责“实际做什么”。C++ 管理器保存绑定 Callable，不持有由 Callable 创建或调用的业务对象。

## 4. 程序中的标签与绑定注册

### 4.1 标签目录与编排标签

程序可以提供只读的标签目录，包含：

- 标签字符串。
- 中文显示名称和说明。
- 接收方或适用场景提示。
- 是否存在业务处理绑定。

目录辅助编辑器选择和诊断。所有实际编排的输出、阻塞输入和全程输入标签仍然完整写在 JSON 中，不通过目录隐式补全。

目录描述和绑定配置均由程序维护，编辑器只能读取。标签存在于目录中，不代表当前时间轴已经配置了对应输入。

### 4.2 绑定内容

建议程序中的一项绑定至少包含以下信息：

| 内容 | 含义 |
|---|---|
| 绑定标识 | 管理器中的唯一标识，用于注销和运行时定位 |
| 接收标签 | 按完整字符串匹配的标签 |
| 接收范围 | 时间轴输入接收方或其他系统接收方 |
| Callable | 收到标签后执行的项目回调 |
| 程序依赖 | 项目回调调用的服务和业务对象，由项目自行管理 |

接收范围属于代码中的路由注册，不增加 JSON 目标字段。建议把时间轴输入接收与其他系统接收明确区分，避免时间轴输出被误当作发送方自己的有效输入。

同一个标签可以注册多个处理逻辑；同一处理类也可以用于多个标签。建议按注册顺序稳定调用，每项绑定拥有独立标识，不配置 JSON 优先级。

### 4.3 注册和注销时机

推荐接入顺序：

1. 创建时间轴系统及其事件管理器。
2. 项目程序注册标签目录和 Callable 绑定。
3. 加载 JSON 编排定义。
4. 创建并启动所需的时间轴运行实例。
5. 时间轴按配置激活接收入口，管理器开始正常派发。

项目模块退出时注销自身绑定，并清理由项目创建的异步回调。插件不会替项目取消业务对象。

JSON 加载器不负责注册 Callable。可视化编辑器不负责创建业务处理对象。

项目可从 GDScript、C# 或其他 Godot 脚本代码注册 Callable；语言封装由项目按需提供。

### 4.4 当前统一请求入口

所有回调触发的标签和控制操作都可以通过 `NVTimelineService.submit_request(Dictionary)` 加入同一 FIFO 队列。操作类型共 9 类：

| 操作 | 职责 |
|---|---|
| publish_label | 提交标签，可选指定目标时间轴 |
| start_timeline | 请求启动时间轴 |
| pause_timeline | 请求暂停时间轴 |
| resume_timeline | 请求恢复时间轴 |
| stop_timeline | 请求停止时间轴 |
| advance_clock | 请求推进时钟 |
| fast_forward | 按序求值至绝对位置，阻塞通过后继续到目标 |
| jump | 向前跳至绝对位置，略过经过的标记 |
| resolve_output_result | 为等待结果的输出返回成功或失败 |

绑定注册和查询状态仍使用各自的专用 API，不属于队列请求类型。旧的 Service 直接控制方法为兼容保留；在事件 Callable 中应使用统一请求入口。

## 5. 输入有效性与业务绑定的关系

代码中存在标签绑定，并不意味着任何时刻都触发某条时间轴的处理。

对于时间轴输入，必须先根据该时间轴的 JSON 配置和运行状态确认接收入口有效，再调用对应业务绑定。

- 全程输入已删除、禁用，或本次运行已结束，则不通过该入口调用处理类。
- 禁用轨道中的阻塞输入不参与接收和等待。
- 阻塞输入需要本次运行的期待标签记录，不能继承上一次运行的结果。
- 普通阻塞输入即使没有业务绑定，框架仍然可以接收标签并解除等待。
- 全程输入没有绑定业务处理时，应给出诊断；框架不猜测其应该暂停还是停止。

其他系统的接收方按程序注册的有效期接收输出标签，无须伪装成时间轴输入标记。

输入是否被接收与业务处理是否执行成功是两个状态。某个处理类报错，不能自动改变其他输入的接收记录或绕过后续阻塞标记。

## 6. 统一通信流程

### 6.1 时间轴输出到其他系统

以解谜为例：

1. 时间轴经过配置的输出标记，发出 puzzle_start。
2. 管理器按标签调用项目注册的 Callable。
3. 项目回调执行界面和解谜逻辑，并自行管理交互过程。
4. 如果输出标记设置了 `wait_for_result`，回调完成后提交成功或失败；成功继续时间轴，失败停止本次运行。
5. 需要表达具体业务分支时，项目回调可以提交不同标签，由时间轴上配置的输入标记接收。

JSON 记录 `puzzle_start` 输出标记及其是否等待结果。解谜逻辑、Callable 绑定和输入标签由项目管理。

### 6.2 其他系统输入到时间轴

其他系统通过统一请求入口发出 urgent_interrupt。时间轴运行时确认其全程输入有效，管理器再调用程序绑定的 Callable。

项目回调可以提交暂停、停止或其他请求。具体“中断”含义由项目代码定义，不由标签名称推导，不在 JSON 中配置 action。

### 6.3 时间轴之间通信

多个文件共同运行属于后续扩展，当前一个 Service 只装入一个时间轴文档。未来多个时间轴同时存在时，A 输出 desktop_notice，B 若配置了有效的同名输入，可以通过同一标签请求接收。

项目回调通过 Service 的 `submit_request` 请求目标时间轴启动、暂停、恢复或停止。请求按队列顺序处理，不要求回调直接访问目标时间轴对象。

标签默认广播；`target_timeline_id` 可将标签限定到指定时间轴。JSON 输出不保存目标，由程序提交消息时决定。

## 7. 运行时消息与处理上下文

输出配置只有标签，运行时可以附加管理通信所需的内部信息。这些信息是内存对象字段，不是另一份事件 JSON。

建议上下文能够提供：

| 信息 | 用途 |
|---|---|
| 触发标签 | 项目 Callable 判断收到什么输入 |
| 来源标识 | 区分哪个运行实例或系统发出了标签 |
| 所属时间轴运行标识 | 让处理操作作用于正确的运行实例 |
| 输入入口标识 | 定位触发的是哪个阻塞标记或全程输入 |
| 当前逻辑时间 | 提供发生位置，不查询系统钟面作为剧情时间 |
| 输出标记标识 | 让业务回调为正确的等待输出返回成功或失败 |
| 是否等待结果 | 区分普通输出和阻塞输出 |
| 程序注入的服务接口 | 接入具体 UI、业务系统和其他对象 |

项目回调使用 `submit_request` 提交标签、时间轴控制和输出结果。输出结果通过时间轴 ID、运行 ID、标记 ID 关联，不创建单独的插件事件执行对象。

编排中的全部配置对象 ID 使用程序生成的 int，由 JSON 文档的 id_counter 统一自增分配，自增结果为负数时拒绝分配。该计数器属于文档模型，不由事件管理器分配；运行标识、执行标识和代码绑定标识不消耗它。标签仍为字符串，业务绑定方式不变。

JSON 不存储上下文、对象指针、节点路径、消息来源、队列内容和执行状态。输出标记只增加静态 `wait_for_result` 配置，不保存业务结果。

## 8. 事件处理基类与生命周期

本节从这里开始的处理基类、处理实例、桥接、生命周期状态机和取消规则，全部是早期备选设计，现阶段已由“业务 Callable 自行管理异步过程，插件只等待布尔结果”的实现口径取代。它们仅为保留历史讨论，不应作为当前实现或待实现清单；当前契约以第 2.4 节、第 4.4 节和第 9 节为准。特别是，插件不创建、持有或追踪项目的事件处理实例。

### 8.1 C++ 核心与脚本扩展层

当前方案优先向项目提供 C# 基类。建议继承关系为：

~~~text
Godot.RefCounted
└── TimelineEventHandler.cs：插件提供的 C# 基类
    └── InterruptEvent.cs：项目中的具体派生类
~~~

C++ 自定义 GDExtension 类不能直接按普通 C# 类的方式作为项目脚本基类使用。当前引擎的 C# 接入通过引擎内置基类包装 GDExtension 对象，因此选择 Godot 自带 RefCounted 作为脚本基类的原生承载类型。

这允许项目在插件目录之外编写 C# 派生类，同时保持事件调度和生命周期集中在 C++ 核心中。不需要项目另建一套 GDExtension 来实现普通业务事件。

如果支持 GDScript，可提供独立的 timeline_event_handler.gd 基类，同样继承 RefCounted，通过 GDScript 桥接提交工厂和回调。C# 和 GDScript 基类不能互相继承，但可以实现相同的执行、取消和报告约定。可选 GDScript 支持不改变第一版以 C# 为主要扩展入口的决定。

### 8.2 基类契约与项目示例

建议脚本基类提供以下入口：

| 入口 | 含义 |
|---|---|
| Execute(context) | 接收脚本上下文，开始处理一次有效触发 |
| Cancel() | 停止本次处理、断开回调并释放临时资源；无清理需求时可使用基类默认实现 |
| context.Complete() | 请求 C++ 管理器登记正常完成 |
| context.Fail(...) | 请求 C++ 管理器登记失败 |
| 上下文标签与控制接口 | 发出标签、请求暂停或停止，不直接修改运行时内部状态 |

一个处理实例的 Execute 入口只调用一次。同步完成和异步完成均通过上下文报告，由 C++ 管理器登记终态。

以下代码仅描述预期使用方式，相关类型和 API 尚未实现，不表示当前项目已经可以编译或运行这些示例。

插件基类示意：

~~~csharp
using Godot;

/// <summary>
/// 插件提供的 C# 事件基类，供项目继承；执行状态由 C++ 管理器维护。
/// </summary>
public abstract partial class TimelineEventHandler : RefCounted
{
    /// <summary>
    /// 开始处理一次有效触发；由桥接层传入包装后的运行时上下文。
    /// </summary>
    public abstract void Execute(TimelineEventContext context);

    /// <summary>
    /// 取消时释放本次处理的回调、临时对象等；派生类可以覆盖此入口。
    /// </summary>
    public virtual void Cancel()
    {
        // 默认事件没有额外资源；需要清理的派生类自行实现。
    }
}
~~~

项目派生事件示意：

~~~csharp
/// <summary>
/// 项目中的紧急中断事件，通过插件接口暂停当前所属时间轴。
/// </summary>
public partial class InterruptEvent : TimelineEventHandler
{
    /// <summary>
    /// 收到绑定标签时执行，完成后交还给 C++ 管理器处理生命周期。
    /// </summary>
    public override void Execute(TimelineEventContext context)
    {
        // 将暂停请求提交到统一控制队列，作用于本次执行所属的时间轴。
        context.PauseTimeline();

        // 本次处理立即完成，不隐式发出任何业务完成标签。
        context.Complete();
    }
}
~~~

项目程序注册示意：

~~~csharp
// events 表示插件提供的 TimelineEvents 包装对象；绑定仅存在于程序中。
events.Register("urgent_interrupt", () => new InterruptEvent());
~~~

异步事件可以保存本次上下文，在收到业务回调后发出结果标签并报告完成。不能直接用 async void 绕开异常报告和取消清理；具体异步辅助接口由后续实现确定。

### 8.3 Callable 桥接与对象所有权

建议桥接把程序注册转换为三项统一调用能力：

| 跨语言能力 | 桥接职责 |
|---|---|
| 工厂 Callable | 调用项目注册的工厂，返回一个 RefCounted 处理对象 |
| 执行 Callable | 接收处理对象和原生上下文，调用 C# Execute，并包装为 TimelineEventContext |
| 取消 Callable | 调用对应处理实例的 Cancel，结束其业务回调和临时资源 |

C++ 管理器根据执行标识关联处理对象和回调，C# 桥接负责解释脚本类型。执行入口通过桥接调用，不要求 Godot 直接把自定义的 C# 上下文对象编组为 Variant。

桥接应捕获脚本执行异常并向管理器报告失败，不把异常当作正常完成。GDScript 适配层遵守相同的生命周期和上下文规则，其错误报告方式需要在原型中验证。

管理器需要在整个执行有效期内持有处理对象的原生引用，以及能够保持托管对象和回调有效的桥接记录。不能只保存弱引用，让仍在运行的事件被 .NET 回收。

进入终态后，按约定清理业务回调、原生引用和 Callable 捕获的托管引用。取消和释放属于确定的执行管理动作，不能单靠 C# GC 代替。

上下文与执行标识共同校验有效期。处理实例保留了上下文对象，不代表它在终态或时间轴停止后仍有权限发出业务结果。

### 8.4 建议的实例创建策略

建议默认每次被接受的业务触发创建独立的处理实例和执行标识。多个事件允许重叠执行，不因共用标签或处理类而共享运行状态。

程序注册的是工厂或处理类型，不是供全部时间轴共用的可变执行对象。

实例复用、重复触发合并或拒绝等策略如果以后需要，应由程序确定，不加入 JSON。默认创建策略仍属于工程建议，未作为用户已确认行为。

### 8.5 生命周期状态

建议使用以下独立于时间轴标记和视觉事件段的处理生命周期。状态存储与转移由 C++ 管理器负责，脚本基类不另建一套生命周期状态机：

~~~mermaid
stateDiagram-v2
    [*] --> Created
    Created --> Running
    Created --> Cancelled
    Created --> Failed
    Running --> Completed
    Running --> Failed
    Running --> Cancelled
    Completed --> Released
    Failed --> Released
    Cancelled --> Released
    Released --> [*]
~~~

| 状态 | 含义 |
|---|---|
| Created | 管理器已创建对象，尚未进入执行入口 |
| Running | 正在同步执行，或等待异步结果 |
| Completed | 处理正常结束 |
| Failed | 初始化或执行失败 |
| Cancelled | 处理被显式取消，或所属运行已结束 |
| Released | 回调、资源和管理器记录已清理 |

管理器统一更新状态。处理实例通过报告接口请求状态改变，不直接改写管理器的内部记录。

终态报告应具备幂等性。重复完成、取消后完成、旧执行迟到回调不能重新激活执行。

### 8.6 事件完成与业务标签

处理实例完成不自动等于某个阻塞标记收到结果。管理器的完成登记负责生命周期；业务流程需要哪个完成标签，由处理程序显式发出。

例如解谜程序发出 puzzle_completed 后报告处理结束。管理器不会根据处理类名或执行标识猜测完成标签。

### 8.7 暂停、停止与系统退出

- 时间轴暂停不自动取消已有业务处理。处理对象是否暂停自身任务，由其程序逻辑决定。
- 暂停和阻塞等待期间，全程输入继续有效，处理实例仍可回传结果或控制请求。
- 解除某个阻塞原因，不应自动解除用户或程序设置的其他暂停原因。
- 停止某次时间轴运行时，撤销其输入入口，取消所属未结束执行，并清理接收记录。
- 一份定义再次运行时，使用新的运行标识，不继承旧处理实例和接收结果。
- 系统销毁时，先禁止新执行，撤销注册和监听，取消存量执行，再释放处理实例与管理器。

如果 Service 是 Autoload，场景退出需要显式结束属于该场景的运行和绑定，不能依靠 Service 自动销毁。

异步回调应携带可校验的执行标识。对象或运行已经结束时，迟到回调被忽略或记为诊断，不持有失效的场景对象继续调用。

脚本事件取消时，管理器调用桥接的取消入口；脚本负责移除自己的业务回调，管理器负责执行记录和原生对象引用。C# 重新编译或运行结束后，不复用上一次运行留下的托管对象和 Callable。

## 9. 调度、阻塞与错误处理

### 9.1 消息队列

标签、时间轴控制、时钟推进、快进、跳转和输出结果统一进入 FIFO 请求队列，避免在遍历标记或回调过程中递归改写当前运行状态。

同一队列中的请求按稳定顺序派发。回调新产生的请求进入队尾，不在当前函数栈中递归执行。

单轮派发上限为 1024；达到上限时记录诊断，剩余请求留到下一帧，避免标签或控制请求形成无限循环。

### 9.2 时间轴标记求值

普通时钟推进和快进都按时间求值经过的标记，不能只检查推进后的终点。

遇到未收到标签的阻塞输入，或等待结果的输出未返回结果时，不能继续处理更晚的标记。普通时钟推进遇阻时丢弃本次剩余量；快进则保留本次目标，阻塞成功解除后继续到目标。

失败结果停止所属时间轴。阻塞和停止不自动影响其他时间轴或共享时钟。

跳转只允许向前，直接略过目标位置及之前的标记，不发标签、不等待阻塞输入；跳到有限时长末端会完成时间轴。

### 9.3 错误处理

无效请求、缺少目标、过期输出结果或循环派发会记录诊断。

业务处理失败由项目回调显式返回 `success: false`。插件不会捕获或解释业务结果细节；等待输出未收到结果时会持续等待，项目可以自行决定是否发出失败结果。

输入未绑定业务类与阻塞输入未收到标签是不同情况。普通阻塞输入无需业务类即可等待和通过。

## 10. 编辑器与程序的边界

时间轴可视化编辑器采用类似 Unity 插件的独立弹出窗口。窗口由 Godot EditorPlugin 打开，作为非模态的独立 Window 运行；它负责编辑 JSON 编排，不以内嵌 Dock 作为主要编辑区域，也不因为打开或关闭窗口而改变运行时事件管理器的状态。

编辑器允许：

- 添加、删除、移动、调整长度、改名和改颜色等纯视觉事件段编辑。
- 添加、删除和移动输出与阻塞标签标记。
- 添加、删除和启用全程输入标签。
- 编辑与 JSON 对应的时钟、时间轴和轨道属性。
- 从只读目录选择标签，查看中文说明和当前代码绑定状态。

编辑器不允许：

- 手动修改程序生成的配置对象 id 或文档分配计数器 id_counter。
- 修改标签与处理类的代码绑定。
- 指定脚本路径、函数名或处理实例工厂。
- 配置事件实例生命周期和对象所有权。
- 将运行时消息、接收记录或执行状态写回 JSON。

如果当前编辑环境没有加载项目的标签目录，应显示文件中原有的标签，不能删除未知标签或保存时丢失配置。

## 11. Godot 插件与语言实现边界

通用部分全部位于 addons/nv_timeline/，包括：

- 时间轴系统与时钟运行时。
- 事件管理器、统一请求队列和 Callable 上下文。
- 输出等待结果校验，以及通用时间轴控制请求。
- 通用的暂停、停止、发出标签等处理能力。
- JSON 读写和可视化编辑器基础设施。
- 插件构建文件、源码、二进制和示例。

如果采用 native 子目录，应该位于 addons/nv_timeline/native/，不把本插件通用源码放到项目根目录的 native/ 中。

项目中的 C# 派生处理类负责解谜、桌面应用和具体剧情等业务逻辑；其代码中完成标签绑定和服务注入。插件不依赖当前项目的 UI 插件或业务单例。

建议语言分工：

| 部分 | 语言 |
|---|---|
| 时钟、时间轴运行时、事件管理器、消息队列、执行状态 | C++ |
| JSON 读写、片段数据模型和可视化编辑器核心 | 优先 C++ |
| 项目业务 Callable 和异步状态 | 由项目按需要选择 C# 或 GDScript |
| 可选编辑器胶水 | 仅在 Godot 编辑器扩展需要时使用 GDScript |

项目业务 Callable 留在使用方项目代码目录；插件只暴露稳定的 C++/Godot API，不提供事件处理基类或托管生命周期桥接。

所有新增代码必须有详细的中文注释。

## 12. 实现验收建议

运行时验收至少覆盖：

1. 输出、阻塞输入和全程输入标签均从 JSON 完整加载，没有处理类绑定字段。
2. 程序注册绑定后，全程输入可以在任意运行位置触发处理，暂停期间仍能接收。
3. 删除或禁用输入入口后，该时间轴不再通过该入口执行处理；其他时间轴正常接收。
4. 阻塞输入未收到标签时停在标记位置，收到期待标签后解除等待。
5. 普通阻塞输入没有业务处理类时也能通过框架完成等待。
6. 同一处理类型用于并行时间轴时，执行状态互相独立。
7. 阻塞输出携带时间轴 ID、运行 ID 和标记 ID；成功继续，失败停止。
8. 重新运行后旧运行的输出结果被拒绝。
9. 九类请求都从统一 FIFO 处理，指定目标的标签不会投递给其他时间轴。
10. 快进遇输入或输出阻塞时保留目标，成功解除后继续到目标。
11. 向前跳转跳过期间标记且不补发标签，跳到末端会正确完成。
12. 普通时钟推进遇阻塞仍按既有规则丢弃本次剩余单位。
13. 视觉事件段的修改不产生业务事件，不改变标签绑定。

## 13. 尚待确认的细节

- 是否需要将项目回调的异常原因作为诊断文本提交；时间轴仍只接受成功/失败两种结果。
- 多个代码绑定收到同一等待输出时，由业务侧保证只有协调后的单一结果；运行时采用首个有效结果。
- 多文件装入同一 Service、跨文件时钟 ID 作用域与文档卸载策略，暂缓到后续扩展阶段。
- 跳转当前只支持向前；将来若增加倒退跳转，需要另行定义已收标签和重复越过标记的处理方式。

快进遇到阻塞后保留原目标，收到成功结果后继续；普通时钟推进遇到阻塞仍丢弃本次剩余推进量。两者的行为已经分别确定。

## 14. 语言互操作依据

- 当前引擎的 C# 接入在 setup_csharp_script_binding 中通过引擎内置基类包装 GDExtension 对象；本方案不依赖直接继承自定义 C++ GDExtension 类型：[Godot C# 接入源码](https://github.com/godotengine/godot/blob/master/modules/mono/csharp_script.cpp)。
- C# 和 GDScript 可通过 Godot 对象、方法和信号通信，但不能直接互相继承脚本基类：[Godot 跨语言脚本文档](https://docs.godotengine.org/en/latest/tutorials/scripting/cross_language_scripting.html#inheritance)。
- 跨原生边界仅传递 Godot 支持的类型，脚本上下文包装留在 C# 侧：[Godot C# Variant 文档](https://docs.godotengine.org/en/latest/tutorials/scripting/c_sharp/c_sharp_variant.html)。

这些依据用于界定方案的语言边界；实际桥接行为仍需在使用的 Godot 4.8 自定义构建中完成原型验证。
